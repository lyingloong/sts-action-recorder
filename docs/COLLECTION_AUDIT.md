# 采集验收

本页用于首次安装、更新 Mod 或依赖后检查实际记录。代码测试检查结构和补丁兼容性，
实际游玩用于确认入口覆盖；两者各有用途。安装与配置见 [使用指南](USER_GUIDE.md)。

## 验收准备

1. 启用 ActionRecorder、BaseMod 和推荐的 CommunicationMod，重启游戏加载目标 jar。
2. 在 Mod 设置中开启动作提示和当前可选动作提示，便于对照实际操作。
3. 记录游戏、Mod、CommunicationMod、BaseMod、ModTheSpire 版本及代码 commit。
4. 开始一局验收游戏，并记下操作顺序。为覆盖场景可以使用多局，不要求一局遇到所有事件。

## 场景检查

| 场景 | 需要对照的操作 |
| --- | --- |
| 地图 | 首个节点、普通节点、Boss 入口、飞鞋产生的额外可选节点 |
| 战斗 | 同名卡、快速连出、快捷键、结束回合、目标药水、丢弃药水 |
| 战斗内选择 | 攻击/无色药水、发现、燃烧契约、武装、网格/手牌选牌、确认、允许选择零张 |
| 涅奥与事件 | 开局选项、多阶段同下标选项、删牌/转化、翻牌和转盘 |
| 奖励 | 金币、遗物、药水、卡牌奖励入口、选牌/跳过、钥匙二选一、颂钵 |
| 商店 | 点击商人、购买卡/遗物/药水、信使补货、进入删牌、选牌/确认/返回 |
| 营火 | 休息、锻造入口、选牌预览、返回重选、确认、前进，以及可用的特殊营火选项 |
| 宝箱 | 普通和 Boss 宝箱打开、Boss 遗物选择/跳过、获得遗物后立即选牌 |
| 导航 | 奖励后前进、返回、离开、终局返回 |
| 生命周期 | 保存退出再继续同一文件、跨幕同一 run_id、死亡、普通通关、心脏通关 |

自定义 Mod 可能采用其他 UI 或动作入口，应单独添加验收案例。把实际操作与事务逐一
对照，不能仅根据动作总数判断是否漏采。

## 原始日志审计

在本仓库根目录使用任意 Python 3.10+ 环境：

```powershell
python tools/audit_trace.py "C:/path/to/game/data/actionrecorder/run-example.jsonl"
```

该工具只读输入，检查 JSON、序号、对局身份、状态引用、动作事务、执行事件和终局。
输出包含状态/动作计数、场景分布、终局、执行状态、errors 和 warnings。

- 退出码 0：没有结构错误，仍可能有 warnings。
- 退出码 1：有结构错误。
- 缺少完整终局、未闭合事务等可能由中断造成，应按该局用途审查。
- 没有 state_published 会报告错误；仅动作记录仍可用于动作审计，但不是完整状态轨迹。

结构检查不能证明所有动作都已捕获，仍需完成上面的实机对照。

## 状态与动作关联检查

1. `action_begin.before_state_id` 指向实际入口前的消息；地图点击前应为地图场景。
   以 ID 和 context 校验，不能选择“时间上最近”的另一场景状态。
2. 动作实体、卡牌 UUID、位置、目标和选择集合与实际操作一致。商店进入房间与点击商人
   是两个操作，删牌入口与选牌/确认分别记录。
3. 快速出牌/结束回合具有执行跟踪：提交状态保留，执行前状态在逻辑边界单独保存，
   `action_execution_result` 为 executed/skipped/cancelled。accepted 不能代替执行结果。
4. 结算引用存在时检查它指向较后的真实状态；ready 或视觉动画结束并不单独证明效果完成。
5. 取消、返回、拒绝和缺失状态保留为原始记录，下游自行决定如何使用。
6. 非地图状态的 map 为 null；三色钥匙和本幕 Boss 信息应符合实际游戏。
7. 只有真实终局标记整局胜负；跨幕和保存退出保持对局身份。
8. Mod 0.1.2 起，卡牌保留/临时免费/费用修改标记符合游戏对象；非零费用的临时免费牌
   不应被改写成零费用，free_to_play_once 单独记录。
9. 观者切换 Neutral/Calm/Wrath/Divinity 时检查 player.stance；能量/抽牌基数和本回合
   已出牌数按游戏计数记录，快速提交但尚未执行的牌不提前计入。
10. 翻牌前未揭示的 card 为 null；首次翻牌后出现牌面，盖回后保留已知牌面；配对移除后
    保留固定位置并标记 matched；remaining_attempts 与结算时机一致，新事件无旧棋盘记忆。
11. Mod 0.1.3 起，Neutral 的 name=null、未揭示 card=null 等字段在最终 JSON 中存在；
    锻造/删牌预览确认动作的 selected_cards 包含当前目标牌，且与前状态 confirmation_card 一致。
12. 双重打击等自动重放不记作玩家出牌；原攻击的 after_state 应在自动重放结束后。
    单次选牌/确认不再因为鼠标按下阶段多出 game_rejected_or_cancelled 事务。
13. Mod 0.1.4 起，状态中的卡牌保留原始描述和运行时展开描述；遗物、药水、Power 有游戏对象
    提供的描述时应带 `description_source=game_runtime`。检查药水 tooltip 不丢失，未解析卡牌变量
    出现在 `unresolved_description_variables`，不得被静态文本悄悄替换。

字段细节见 [事件格式](EVENT_SCHEMA.md) 和 [状态契约](STATE_SCHEMA.md)。

## 数据集提取验收

对验收日志运行 [提取工具](DATASET_EXTRACTION.md) 后，检查：

- manifest 中角色、进阶、内部种子、结果和文件哈希。
- 所选对局的完整事件与细粒度事务均保留；取消和失败尝试没有被默认丢弃。
- 同一份日志的副本正确去重；保存/继续仍属于同一 run_id。
- 缺失引用为 null 并有 quality_flags，不补造状态。
- 过滤参数选中预期对局，死亡/未完成记录不会混入 victory 筛选结果。

## 验收记录与边界

保存验收原始日志、操作说明、版本、审计报告和已检查场景。遇到问题时保留完整事务及
引用状态，方便复现。正式采集前确认将要覆盖的场景已完成验收。

异常终止、磁盘写入失败或未知 Mod 入口可能导致数据缺失。TCP 无补发，完整数据以
本地记录为基础；原始抽牌堆等引擎信息应由下游按公开信息规则处理。
